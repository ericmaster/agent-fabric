Improve the harness.
Do not re-review the task.

Harness review is a bounded retrospective on how an agent worked: repeated tool errors, stalls, orchestration mistakes or misleading context. It is not business-task acceptance, a continuous monitor or a new execution service.

Reading guide, not policy or a plan. Canonical sources govern behavior; Projektor owns plans, plan amendments and task decisions.

One visible parent. Independent child roles.

The task owner evaluates whether review is useful after verified task closure. When justified, it launches one fresh, visible native review session. That supervisor owns a single review episode; investigation, correction and patch review are sibling children, not a chain of supervisors.

The writer and patch reviewer are conditional. A supported no-change outcome ends without a patch. Child results return to the supervisor; children do not delegate or launch reviews of their own episode.

Existing harness, no daemon

OpenCode/OpenChamber and Pi/PiChamber provide native sessions, history and tools. A short installed instruction pointer prompts evaluation; the full skill loads on demand. No observer, schedule, transcript-import pipeline or model switch is required.

Three separate homes

Git owns executable workflows, contracts and fixes. Native history plus private evidence and audit records support claims. Projektor owns task plans and concise decision comments. This page only explains those relationships.

From execution friction to a verified improvement

  1. 1 · Complete the original task, then evaluate

    Finish deliverables, required checks, authorized delivery, live verification and owned cleanup. Blocked, paused or phase-complete is not finished. Only an explicit early-review request overrides this gate, with the checkpoint labeled incomplete. Expected red tests and productive exploration alone do not justify review.

  2. 2 · Route the role and preserve identity

    The top-level task owner runs the audit source preflight and checks for an existing review of the checkpoint. Reuse that review when present. Otherwise launch one visible native parent; record review_requested, require review_started before history reads, and verify prompt acceptance and visibility. A launch is not PASS.

  3. 3 · Investigate a bounded causal window

    One read-only child examines actual original history and the guidance available at the time—not just the author's final summary. Default budget: at most two friction windows and 12 history/tool retrieval calls, including recovery. Aim for one high-impact correction, two maximum; report inspected/excluded ranges and stop when cause, owner and a safe check are established.

  4. 4 · Correct only a demonstrated cause

    Clear guidance ignored calls for adherence, not another rule. A proven tool bug belongs in its implementation owner. An uncertain selected cause permits one bounded diagnostic child per source/issue. Supported corrections require verified authority, canonical-source edits and regression checks; no speculative cleanup.

  5. 5 · Independently accept and deliver the patch

    A separate writer uses an isolated worktree, then returns a frozen candidate and actual test results. A different child reviews the patch. The supervisor integrates only after acceptance and required checks, rechecks target HEAD/dirty state, verifies managed installation when applicable and closes eligible owned worktrees. At most two cumulative correction starts per original source; resumes never reset the budget.

  6. 6 · Report the bounded outcome

    Record the four checks below, coverage, real session/revision locators and delivery evidence. Summarize problem → correction or justified no-change → validation, with unresolved blockers explicit. Default launch is asynchronous: the source returns the review ID without polling or copying the verdict back unless requested.

A concrete example

An agent repeatedly guesses a CLI flag despite an existing runbook. The investigator compares the failed calls with that runbook. If guidance was already clear, the outcome can be justified no-change. If the documented command is demonstrably stale, an authorized writer fixes its canonical owner, validates the real command and obtains independent patch acceptance. A new monitoring service would not address this bounded cause.

Four checks, not an exhaustive scorecard

evidence_scope

Selected native history establishes the cause, owner and authority—or supports a bounded no-change decision.

improvement_actions

Selected findings are remediated or justified as no-change. Confirmed unresolved causes are not PASS.

verification

Actual focused causal/regression checks support the outcome. Unrun or mocked checks remain labeled as such.

safe_delivery

Claimed integration, applicable managed installation and owned cleanup are verified without touching foreign work.

PASS means only the declared scope passed. Failed checks yield FIX_NEEDED; missing required evidence, capability or authority yields BLOCKED. Only verification/delivery may be not applicable, with a reason. A worker's blocker claim needs an independent supervisor probe and exact boundary before closure.

Audit is a receipt, not proof

skills/harness-review/scripts/audit.py writes private append-only engine JSONL under the user's Agent Fabric state store. OpenChamber uses the OpenCode file; PiChamber uses Pi. Keep session IDs, checks, coverage and revision locators—not raw transcripts, secrets or environments. Retain failures; recording failure stops dependent actions.

Records are agent-reported. Native history and actual command evidence must corroborate success. Counts do not prove all tasks were reviewed, autonomous model compliance or measurable savings.

Authority stays narrow

Carry the user's applicable maintenance authority and canonical owner into the review; task authority alone does not permit global changes. Preserve models, credentials, permissions and foreign work. Product changes need their own scope; production deployment requires explicit approval. Plan-only and report-only instructions still win.

Legacy Jev/spool/plugin tooling is compatibility-only, not the active skill's path. Do not reactivate old observers, import historical learning stores or create recursive retrospectives.

What the user sees at task closure

One concise decision: launched with a real ID; not needed with an evidence-based reason; deferred with the pending gate and owner; blocked with the exact boundary; opted out by explicit instruction; or covered by an existing review. No new status ledger is needed.
