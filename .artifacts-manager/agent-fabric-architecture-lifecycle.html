Choose the owner, not a fixed pipeline

agent-fabric route advises easy → implementor or complex → planner. It does not dispatch agents or watch tests. A planner recommends direct implementation or coordinated slices based on dependencies and integration needs.

Simplified successful execution paths, not a runtime state machine. All paths require a measurable acceptance baseline before edits. Plan-only requests stop at publication; publication alone never authorizes execution.

1 · Plan only what needs planning

The planner inspects current behavior, resolves decision-critical gaps and defines useful, end-to-end testable slices estimated at ≤1 hour each, including tests and review. This is a sizing gate, not a time promise. Required safety stays in scope; optional complexity goes to the existing backlog.

Pin outcomes, checks, evidence locations and rollback before implementation. Verify prerequisites before marking a slice ready. Human-only secret creation is separate; dependent work waits for verified availability.

Plan review checks scope, readiness and routing. Default: at most two passes for a multi-phase plan. Explicit Publish may skip remaining review, but execution handoff still needs current reviewer PASS, no blocking findings and execution authority. The planner does not implement.

2 · Keep implementation and fixes together

The implementor owns diagnosis, edits, required runtime checks and review fixes in one session. Freeze the candidate for an independent, read-only code-reviewer; ordinary fixes resume that reviewer. Later edits invalidate affected checks and review evidence.

A coordinator owns dependencies and integrated acceptance, not product implementation. Workers receive bounded slices, contracts and checks—not whole transcripts. If nested review dispatch is unavailable, the parent invokes the reviewer directly; missing review is incomplete acceptance.

Fresh direct work needs no supervisor ledger. Coordinated work has one macro-state owner; explicit checkpoint continuations retain their history and limits. No nested supervisors or new loop-supervisor tasks.

3 · Repair causes; amend exhausted approaches

Resolve safe, in-scope setup and local/Dev failures under existing authority. Verify a child's blocker instead of forwarding it unchanged. Reuse recorded sessions, diagnoses and unchanged evidence; preserve inherited retry and spending limits.

When recovery is exhausted, return the failed approach, attempts, violated requirement and accepted work through the execution owner to planner Amend. Pause affected writers, revise the relevant specs and baseline, obtain independent plan-reviewer PASS, then resume the existing owner.

An amendment must avoid the diagnosed cause while preserving the objective. Renaming work never resets limits. Unaffected independent work may continue; a genuine external boundary names the exact missing action or decision.

4 · Deliver evidence, not just a patch

Direct implementors own authorized integration and delivery. With coordinated slices, the plan-supervisor owns the combined result. An early smoke or implementation_ready report is provisional; missing, failed, stale or unrun mandatory evidence cannot PASS.

Close with required checks, independent acceptance of the final candidate, scoped commit/integration, retained evidence and eligible task-owned cleanup. Preserve foreign work. Extra QA sessions are discretionary; required runtime or visual checks are not.

Continue already-authorized work without repeated approval. New scope and permission boundaries still apply; production deployment requires explicit human confirmation and rollback/live verification controls. An unfinished stop reports what works, what remains and why, with one reusable status artifact when safely publishable.

5 · Evaluate how the agent worked

After the original task's checks, authorized delivery and cleanup, the top-level owner evaluates harness review and states its decision. Expected red tests or useful exploration alone do not warrant a retrospective. Early review requires an explicit user request.

When justified, one visible review supervisor uses independent child roles to investigate bounded execution friction and deliver a supported correction—or a justified no-change outcome. This improves the harness; it does not re-certify the task. See the specialist harness-review guide for that internal workflow.

Supporting roles and host wiring

Bug-fixer captures and independently reviews a defect report, then routes an executable fix or needs-plan work. Expert-debugger provides a bounded diagnosis when assigned. QA-runner runs selected dynamic checks. Deploy-supervisor owns a separately scoped, authorized post-merge release. None is a mandatory extra layer for every task.

Each fresh child needs a self-contained packet: declared roots, scope, authoritative inputs, permitted paths, checks, evidence and rollback. Missing authoritative inputs stop dispatch; ordinary discoverable setup is work, not a missing contract.

Canonical definitions are rendered by harness adapters; configured hooks enrich task context, publication and checkpoints. Hooks resolve at install/sync, with Markdown preferred over scripts. Portable shell hooks are explicit instructions, not runtime event enforcement. Wait for native completion signals rather than polling agents.

Compatibility: existing loop-supervisor continuations retain their identities, evidence and budgets; they are not the entry point for new work.
