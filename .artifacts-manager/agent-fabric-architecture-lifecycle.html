DECISION VIEW · CURRENT CONTRACTS VS PROPOSED DESIGN

Same human clarity. Fewer places where execution can stall.

Current planned-task route: planner + visual decisions → plan reviewer → projection → plan supervisor → implementor + code reviewer → supervisor reconciliation and delivery. Legacy continuations may additionally contain a loop supervisor; new tasks should not.

Proposed planned-task route: planner + visual decisions → focused plan review → one handoff to an execution owner → implementation, checks and required code review → verified delivery. A coordinator is added only for genuine multi-worker coordination.

“One owner” means one execution/delivery owner, not abolishing human planning or independent review. The planner can remain a separate planning session. For the multi-system Nimblerbot MVP, keep plan review and reviews of auth, persistence and concurrency. Optional review for low-risk work is a proposed policy change, not permission to skip today's gates.

Concrete before / after examples

Illustrative walkthroughs, not claims that these improvements have already happened. Expand each case for the current behavior, exact change and a checkable benefit.

A. “Give me a working Nimblerbot dev preview”

Current

After the explained plan and review, the planner projects phases and launches a plan supervisor. The supervisor constructs a phase packet for the implementor, then reconciles the implementation/review result before integration and preview delivery. The Ops overlay can also prompt for execution again.

Proposed

Keep the same questionnaire, plan and appropriate plan review. Hand one executable slice to one owner: “Create a bot, save its prompt and show it in the authenticated dev preview.” That owner implements, tests, obtains auth/persistence review, integrates and verifies the preview. Remaining requested capabilities stay visible as unfinished scope.

Improvement to verify: one less mandatory coordinating role for this serial slice; no repeated execution prompt. Time to a working preview is measured, not predicted. No claim that the whole multi-system MVP becomes a trivial task.

B. The human chooses “Other” in the HTML questionnaire

Current

The questionnaire captures custom prose, and the planner must transfer its meaning into the executable plan. Multiple later packets can restate that decision differently.

Proposed

The same stable artifact records “Use our existing Bookings integration; do not build a new one.” The plan identifies that decision and its acceptance check. The executor references it directly; only changed decisions are carried on resume.

Improvement to verify: the custom answer appears correctly in the explained plan and implementation check, without re-asking the question. HTML, diagrams, free text and browser QA are retained.

C. Resume after a pause, with no code or scope change

Observed current example

The sampled source continuation rebriefed the same supervisor with four roots, eight required inputs, hashes and mutation allocations before the next action. The underlying child operations were not independently inspected.

Proposed continuation

Resume the same owner. Scope and candidate unchanged. Pending: reproduce the health/claim atomicity finding. Use the existing checkpoint and review finding; preserve the recorded hard budget. No other input changed.

Improvement to verify: no repeated schema discovery, reviewer launch or full packet reconstruction solely because the session resumed. Changed checkout state or expired authority still triggers relevant verification.

D. Reviewer finds a real health-check / action-claim race

Current risk

A finding may travel through supervisor classification, counters, diagnostics and structural-recovery review before another code attempt. Some root-cause analysis is useful; another role boundary is not automatically useful.

Proposed

The same owner reproduces the race, fixes the shared enforcement point, adds a failing-before/fixed-after regression and returns the repair delta to the same independent reviewer. Re-plan only if the fix changes the accepted behavior, scope or material architecture.

Improvement to verify: defect fixed and independently checked without creating another supervisor or splitting one coherent fix into an artificial DAG. Repeated identical failures still stop for diagnosis; hard limits remain enforced.

E. Publishing succeeds remotely, but the response is lost

Current

The native publisher already uses stable identity and readback to reconcile uncertain writes. These safeguards are useful, not ceremony to remove.

Proposed

Keep the publisher's reconciliation. It returns the verified existing task link and plan identity. The owner records that result once and continues; it does not invent another task or build a second receipt hierarchy.

Improvement to verify: exactly one remote parent remains after retry, with the correct plan body. The benefit is simpler orchestration around an existing reliable operation, not weakening the operation.

F. Browser setup fails, or a ledger mirror is unavailable

Current

Browser failures can cross setup/QA role boundaries. The Ops ledger hook attempts secondary replication after local save; replica failure is already non-gating.

Proposed

The owner repairs or selects the documented isolated browser and finishes the required HTML validation. A failed optional mirror stays a side-status; the valid local checkpoint remains authoritative. Enable secondary replication only when it serves a real consumer.

Improvement to verify: browser verification still runs; optional replica failure creates no product retry or user approval request. Existing non-gating behavior is preserved, not claimed as a new capability.

G. Provider quota is genuinely exhausted

Observed current example

Five consecutive hourly attempts failed with actual quota errors. Removing workflow steps cannot create unavailable provider capacity.

Proposed

Keep one recoverable checkpoint and report the actual availability boundary. Resume when capacity returns, or use a separately authorized alternative. Do not create equivalent workers, claim progress or spend another provider's quota without permission.

Improvement to verify: precise status, preserved work and no duplicate workers. No promise of eliminating the genuine wait or proving a smaller model faster.

CONTRACT REVIEW · DIRECTLY OBSERVED

The defaults disagree

Global guidance prefers one native agent and opt-in supervisors. The planner instead requires current plan-reviewer PASS, decomposition and supervisor handoff. Even direct implementor execution requires independent review and a checkpoint protocol.

The planner avoids routine cryptographic trails; the supervisor requires immutable baseline identity and phase closure receipts carrying hashes, episodes, budgets and cleanup proofs. These controls serve valid needs but impose a large fixed cost on small work.

This establishes policy tension, not proof that each rule caused a particular source delay. Resolve the default once in the owning contract and render it consistently.

COUNTEREVIDENCE & LIMITS

Not every blocker is invented

The source has real subscription/credit failures, including a requested Grok review and five later quota errors. Respecting model and spending boundaries was legitimate. No provider switch is authorized by this report.

The original goal includes WhatsApp onboarding, per-bot runtimes, two environments, hybrid flows, APIs and several migrations. That is substantial work even with a simpler harness. Start with one useful end-to-end slice; do not silently delete the remaining product requirements.

PROPOSED DEFAULT · NOT YET INSTALLED

Human-readable planning, then one delivery owner

The owner can use a discovery or review leaf for a distinct question. That leaf does not become another delivery supervisor. Production deployment still requires explicit confirmation.

One readable task contract

  1. Outcome and decisions: visible HTML questions, answers, trade-offs and intended user result.
  2. Context: repository, relevant files and ownership constraints.
  3. Checks: repository gates and meaningful behavioral verification, including the planning artifact.
  4. Authority: reference the actual user authorization once; never infer it from viewing an artifact.
  5. Checkpoint: current revision/diff, passed checks, pending action and real blocker.

Use the same decisions and plan as the human and executor source. Avoid parallel JSON dossiers, repeated baseline reconstruction and routine hash manifests. Preserve content identity where publication idempotency or concurrent writes genuinely require it.

When to add a role

  • Planner: preserve the interactive human-understanding stage for project planning; it need not create a supervisor hierarchy.
  • Plan review: check outcome fidelity, feasibility and material risk; protect human clarity and reject unnecessary machinery.
  • Code review: security, authorization, persistence, concurrency, a required gate or user request.
  • Parallel worker: independent deliverable with a demonstrated benefit; one writer per shared checkout.
  • Deployment specialist: complex release coordination under explicit production authority.

Proposed routing. Current mandatory gates remain in force until canonical contracts change.

Recovery without episode bureaucracy

After a repeated failure, state the failed hypothesis, new evidence and smallest changed approach. If nothing changed, do not rerun. Keep the same owner and reuse passing checks.

Replace mutation-count paperwork with a task-level resource limit only when one is actually assigned. Report a no-progress decision when the approach is exhausted; do not reset hard budgets or manufacture acceptance. Real quota, credentials and scope boundaries remain real.

A smaller model is an experiment

Keep the configured model during this review. In a separately authorized pilot, compare the single-owner route on a similar task using an approved lower-cost model.

Measure time to working slice, user nudges, cost where reported, defects and acceptance. Include whether the human can explain the plan, alternatives and current state. Token reduction is not success if understanding or correctness declines.

Review every role; keep only useful boundaries

Keep the portable compiler

Canonical agents/*.md and adapter mappings remain the source for native harness configuration. Validation, ownership-aware manifests, permission preservation and deterministic rendering are useful infrastructure; the problem is the process being rendered.

Change canonical definitions and owning contracts together, then verify managed installed output. Editing only a generated agent would leave the next sync able to restore the old behavior.
