Proposed workflow

The planner proposes the mode with a short justification; plan review checks it. Large plans get bounded workers, not one enormous context.

Cyan = the selected execution mode. Direct: the implementor owns delivery. Coordinated: the supervisor owns integration and overall delivery; each worker owns its slice's coding, tests and review fixes. No nested supervisors. Exhausted recovery returns through the owner to planning with the existing diagnosis; only affected work is paused.

Four concrete changes

1. Planner recommends the handoff mode

Add a routing recommendation and one-sentence reason to the explained plan. Use implementor for one coherent task; use plan-supervisor for multiple slices with dependencies, parallel work or substantial integration. Plan review can challenge unnecessary coordination.

Example: “Direct: one authenticated preview change.” Or “Coordinated: bot runtime, builder and WhatsApp integration share an API contract.” The choice follows structure, not an arbitrary file count.

2. Make the supervisor a coordinator

Reuse plan-supervisor. It assigns bounded slices, tracks dependencies, resolves cross-slice issues and owns integrated acceptance/delivery. Workers handle their own debugging and review fixes. Remove duplicate worker bookkeeping and routine finding relays.

Example: a worker fixes its failing test locally. An incompatible shared API goes to the coordinator. Only affected dependent work waits; no supervisor is spawned underneath another supervisor.

3. Bound context, preserve continuity

The coordinator keeps the plan, dependencies, accepted revisions, open findings and next actions. Each worker receives only its slice, relevant contracts and checks. Completed slices become compact checkpoints with evidence links, not copied transcripts. Slices may run sequentially or independently in parallel.

Example: the WhatsApp worker receives the accepted bot API contract, not every builder discussion. If direct work reveals genuine coordination needs, hand completed evidence to a coordinator without restarting planning or resetting budgets.

4. Simplify Ops hooks and authorization

“Continue under existing authorization” means no repeated permission prompt for already-authorized scope. Align the decomposition overlay/adapter with the selected mode; preserve publication readback and duplicate prevention. Keep optional mirrors and external pre-review outside the critical path.

Example: “Implement this approved dev plan” authorizes its in-scope work and fixes. Viewing a plan is not execution permission. New scope, spending and production retain their applicable approval boundaries.

Additional rules: explain impact, deliver minimum slices, amend failed approaches

Diagrams explain system impact

For each grilling question, show the affected component, module or product: changed boundaries, data flow, state, deployment or user journey. Selecting an option updates that system view. A question node branching to A/B is not an explanation.

Example: “Shared storage or per-bot storage?” shows where each bot reads/writes, which data is isolated and how provisioning changes—not a diamond pointing to the two answers. Show relevant trade-offs beside the diagram. An unknown “Other” answer stays explicitly unresolved until interpreted; do not invent its effects.

Every slice ends in a minimum viable result

The planner must name one useful behavior, the smallest working path, a reproducible demo/test and what is deliberately deferred. Avoid framework-first phases, bundles of unrelated behaviors and speculative flexibility. A component slice is valid if its real contract can be exercised independently; mocks alone do not prove integration.

Example: “Create one bot, save its prompt and run one sandbox conversation” precedes “all channels, generic workflow engine and migration of every bot.” Later capabilities remain in the plan. Auth and tenant isolation required for that first path are not optional.

Exhaustion triggers plan amendment

When recovery iterations are exhausted, reuse the dispatched diagnosis and send its result to the planning owner. If diagnosis is still running, wait for it rather than launch a duplicate. Return the failed approach, attempted fixes, violated requirement, accepted work and smallest plausible alternative.

Example: a generic action scheduler repeatedly fails atomicity checks. Planning may replace it with one durable serialized command path that meets the same concurrency and reliability objective, deferring general scheduling only if the objective permits it. Review the amendment, then resume the affected slice.

Planner and plan-reviewer definition changes

Planner: produce minimum viable slices, not merely “vertical” ones. For each: what works at the end, how we demonstrate it, why this is the minimum, and what comes later. Classify outcome constraints separately from suggested implementation. Support an amendment of affected in-flight phases instead of rejecting all refinement of approved plans.

Plan reviewer: ask “Can anything be removed while preserving this slice's useful result?” Reject phases that only prepare infrastructure without an exercisable result, or accumulate unrelated capabilities. Prefer subtraction or a smaller alternative over new machinery. Review amendments against the original objective, diagnosis and revised checks—not against an obsolete implementation suggestion.

Flexible specs, explicit revisions: algorithm, library, internal architecture, phase boundaries and implementation-specific tests may change when evidence supports a better minimum solution. Update the owning spec and affected acceptance criteria before further implementation; retain the reason and prior failures. Do not mark old failed checks as passed, or silently remove required product behavior.

Existing definitions already say “smallest coherent approach” and prohibit bloat, but do not require this per-slice minimum-result test. Planner's blanket restriction on refining approved/in-flight plans conflicts with evidence-backed amendment. The questionnaire template guidance also explicitly describes decision-tree fragments; that wording must become system-impact views.

Keep replanning from becoming another endless loop

Reuse the same planning/reviewer sessions and accepted checkpoints. An amendment must explain how it avoids the diagnosed cause and provide a genuinely different, testable approach. Preserve cumulative history and hard spending/safety limits; define a bounded implementation allowance for the amended approach. Rewording a plan or renaming a slice does not renew a budget.

An in-scope alternative proceeds under existing authority after review, without another routine permission request. If no objective-preserving alternative exists, report the specific product decision, unavailable capability or hard limit. Do not retry the same failure through repeated planning cycles. Independent unaffected slices can continue.

What does not change

HTML questionnaires and explanations · free-text human decisions · browser validation · original plan/task objectives · required behavior and safety constraints · independent plan/code review for this MVP · explicit production confirmation · real permission and spending boundaries · no false PASS.

Implementation suggestions are revisable; the objective is not silently negotiable. Relevant checks follow an explicitly reviewed spec amendment. Genuine quota failures still require capacity or an authorized alternative.
