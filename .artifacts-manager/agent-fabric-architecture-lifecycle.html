CONTRACT REVIEW · DIRECTLY OBSERVED

The defaults disagree

Global guidance prefers one native agent and opt-in supervisors. The planner instead requires current plan-reviewer PASS, decomposition and supervisor handoff. Even direct implementor execution requires independent review and a checkpoint protocol.

The planner avoids routine cryptographic trails; the supervisor requires immutable baseline identity and phase closure receipts carrying hashes, episodes, budgets and cleanup proofs. These controls serve valid needs but impose a large fixed cost on small work.

This establishes policy tension, not proof that each rule caused a particular source delay. Resolve the default once in the owning contract and render it consistently.

COUNTEREVIDENCE & LIMITS

Not every blocker is invented

The source has real subscription/credit failures, including a requested Grok review and five later quota errors. Respecting model and spending boundaries was legitimate. No provider switch is authorized by this report.

The original goal includes WhatsApp onboarding, per-bot runtimes, two environments, hybrid flows, APIs and several migrations. That is substantial work even with a simpler harness. Start with one useful end-to-end slice; do not silently delete the remaining product requirements.

PROPOSED DEFAULT · NOT YET INSTALLED

One owner, from clarification to verified result

flowchart LR
A[Clarify outcome] --> B[One owner implements and tests]
B --> C{Material risk or required review?}
C -- yes --> D[One focused independent review]
D -- concrete defect --> B
C -- no --> E[Verify and deliver]
D -- accepted --> E

The owner can use a discovery or review leaf for a distinct question. That leaf does not become another delivery supervisor. Production deployment still requires explicit confirmation.

Small task contract

  1. Outcome: observable user result and what is out of scope.
  2. Context: repository, relevant files and ownership constraints.
  3. Checks: required repository gates plus the smallest meaningful behavioral verification.
  4. Authority: what may be changed or deployed; preserve actual permission boundaries.
  5. Checkpoint: current revision/diff, passed checks, pending action and real blocker, if any.

No separate baseline JSON, phase ledger or hash manifest for routine work. Git and native command/session evidence remain available. Stronger provenance stays where the actual task needs it.

When to add a role

  • Planner: unresolved architecture or a genuinely multi-deliverable project, or a plan-only request.
  • Plan review: irreversible choices, significant spending, migrations or cross-system risk; not prose polishing.
  • Code review: security, authorization, persistence, concurrency, a required project gate or explicit user request.
  • Parallel worker: independent deliverable with a demonstrated benefit; one writer per shared checkout.
  • Deployment specialist: release complexity merits one, under explicit production authority.

These are proposed routing rules. Current mandatory gates remain in force until the canonical contracts are changed.

Recovery without episode bureaucracy

After a repeated failure, state the failed hypothesis, new evidence and smallest changed approach. If nothing changed, do not rerun. Keep the same owner and reuse passing checks.

Replace mutation-count paperwork with a task-level resource limit only when one is actually assigned. Report a no-progress decision when the approach is exhausted; do not reset hard budgets or manufacture acceptance. Real quota, credentials and scope boundaries remain real.

A smaller model is an experiment

Keep the configured model during this review. In a separately authorized pilot, compare the single-owner route on a similar task using an approved lower-cost model.

Measure time to working slice, user nudges, cost where reported, defects and acceptance. Do not infer dollars from a zero-valued subscription cost counter or use token reduction as a substitute for correctness.

Review every role; keep only useful boundaries

Click a role for its current obligation, proposed disposition and canonical edit target. Recommendations are not deployed behavior.

Keep the portable compiler

Canonical agents/*.md and adapter mappings remain the source for native harness configuration. Validation, ownership-aware manifests, permission preservation and deterministic rendering are useful infrastructure; the problem is the process being rendered.

Change canonical definitions and owning contracts together, then verify managed installed output. Editing only a generated agent would leave the next sync able to restore the old behavior.

The previous artifact still showed loop-supervisor as the normal route, mandatory QA and a fixed five-mutation scope cap. Current source instead deprecates new loop supervisors, makes QA discretionary and permits bounded renewed episodes. This update removes that misleading snapshot.

Success means delivery improves

  • First useful runtime result arrives before orchestration expands.
  • No routine “please continue” prompts needed between authorized steps.
  • Review findings cite material defects, not formatting or new scope.
  • No repeat full review or full test suite without changed inputs or a real verification requirement.
  • Failed checks stay failed; production approval, secret handling, foreign work and spending boundaries survive simplification.
